# Safety model

An agent that reads logs and can change a cluster is a prompt-injection target. A log line can say "scale this to zero". The controls are layered, and the important ones sit **outside the model**:

| Layer | Control |
|---|---|
| Cluster access | Each cluster in a Contract is either `in_cluster: true` or names its `context` explicitly. The agent never falls back to your current kubectl context. A kubeconfig credential plugin is refused unless the cluster sets `allow_exec`. |
| RBAC | Read-only ClusterRole, bound **per namespace** with RoleBindings. No Secrets, no ConfigMaps. CI checks this by impersonating the ServiceAccount ([`demo/rbac-check.sh`](../demo/rbac-check.sh)). |
| Write scope | Write tools are opt-in per Contract (the kubernetes integration's `enable_actions`). When off, the write tools aren't registered at all. When on, they cover only `pods/eviction` (respects PodDisruptionBudgets) and `deployments/scale`. There's deliberately no `patch deployments`, which would allow changing images and commands. |
| Actuator | Opt-in per cluster (`actuator_token_secret`). It runs in the client's cluster with its own ServiceAccount and token, never the Relay's: it can resize pods (`pods/resize`: requests, and a limit only as a Reflex, [ADR 0005](adr/0005-reflexes-may-raise-limits.md); never images or commands), evict a pod whose resize is Infeasible (`pods/eviction`, through the Eviction API so PodDisruptionBudgets hold; only with the Contract's `actuator: eviction` on, inside its windows, one pod at a time, 5 minutes apart, and never a StatefulSet's, DaemonSet's or Argo Rollout's pod, or a pod of a Deployment with one replica or that no PodDisruptionBudget covers), report the facts of pods that may block a node's removal when they change, hourly at least (names, volumes' names, three annotations: [Blockers](client-cluster.md#blockers-what-the-actuator-reports)), create Events and keep one ConfigMap of its own, bound per namespace, and nothing else. Its reads are the Contract's namespaces' too, but for one Role in `default` (in `deploy/actuator/rbac.yaml`, and a client may remove it): Events there, where a Node's are, to tell a node out of memory from a container at its limit (`reflexes.oom`, which for now only reports OOM kills); and one ClusterRole listing nodes (`squero-actuator-nodes`, which a client may remove too), of which it sends only the values of the label keys its pods' nodeSelector and node affinity name, for the Hub's [nodes that could go](optimizer.md#nodes-that-could-go); and one Role reading its own pod in its own namespace (`squero-actuator-self`, `get pods`, which a client may remove too), whose facts it sends as any pod's. It applies only what the Hub approved, one Sizing at a time or under Automation (a Sizing rule with `automate: true`, the Operator's standing approval in the contracts repo, ADR 0004), never a request above the container's limit, and nothing while the Kill switch is on or on a Workload a person paused (`squero-actuator/pause: "true"`). A CronJob's pods are never resized in place: only its runs' new pods get the held requests, from the webhook. Three Rollbacks of a Workload in 7 days end its Automation. Its reports are data to the Hub, as a client's alerts are: stored for its own cluster's namespaces only (but for its own pod, `itself`, from its own namespace), refused for a number that isn't one, dated no later than they arrived, shown in Slack as text (no mention, no link), and at most 20 Rollbacks of a cluster posted in an hour. The Operator's Revert (`revert_sizing`, refused under the Kill switch) puts a container's pods back to their template's requests and stops its Automation until the next approval. Its pod-creation webhook fails open (`failurePolicy: Ignore`, 2 s), sees only the Contract's namespaces, and never touches `kube-*` or its own namespace. With the Contract's Placement on a cluster it also gives new pods of the Workloads the Hub lists a preferred node affinity for the Pinned nodes and a toleration of their named taint: never a requirement, never a running pod ([ADR 0006](adr/0006-placement-is-a-preference.md)). With a cluster's spot nodes and a Spot ratio it steers new replicas of the Workloads the Hub lists: a preference for spot nodes, or, for the replicas its On-demand minimum keeps, the one requirement it ever adds, "not on a spot node", with a label, a deletion cost of 1 and the spot taint's toleration; never a running pod. A CronJob's runs under `spot: true` prefer spot nodes on a run's first tries and are required off them once the run has a failed pod, only where its Jobs allow a retry. |
| Contract scope | Every tool checks its `cluster` and `namespace` against its own Contract server-side, on top of RBAC. Each Contract's alerts arrive on their own URL with their own token ([Contracts](contracts.md)). The Hub's own Prometheus reads for Sizings name the Contract's namespaces in every query, with one exception: a node's Room ([Nodes](optimizer.md#nodes)) needs every pod on the node, so pods outside those namespaces are read as one sum and one count per node, added up by Prometheus, never by name or namespace, and not at all from a Prometheus another Contract reads without cluster labels. |
| Human approval | The Hub keeps its own list of what each tool does ([ADR 0002](adr/0002-hub-and-relay.md)). A tool not on the list is hidden from the agent. `HumanInTheLoopMiddleware` interrupts before every tool the list marks as a write, **and** before every tool whose server doesn't claim `readOnlyHint`. A server's annotation can only make a tool stricter, so a server that mislabels a write as read-only still waits for approval. The reviewer sees the full arguments. |
| Secrets in context | Env var *values* are never returned, only names. Logs and events are redacted (tokens, JWTs, keys, `password=`), and so is every request to the model, alert labels and Questions included. |
| Client identifiers | A Contract's Data policy can mask its hostnames, names, emails and IPs: the LLM provider sees placeholders, everyone else the real values ([Masking](contracts.md#masking)). |
| Prompt injection | Alerts and tool output are framed as data. An eval scenario plants an instruction in pod logs, and it fails if the agent even *attempts* a write. |
| Blast radius | Per-run tool-call and model-call limits. The model sees at most `SQUERO_TOOL_OUTPUT_LIMIT` characters of any tool result at once; a larger one is kept, redacted, in that Investigation's state, and `read_more` pages or filters it. The receiver runs a bounded number of triages at once. |
| Auth | Two tokens: Alertmanager's token can only submit alerts. Reading reports and deciding on proposed actions needs the approver token. |
| Audit | Every tool call is logged as one JSON line and counted in `squero_tool_calls_total{tool,status}`. A triage's executed actions are recorded where the tool ran, never taken from the model's own account, and an approved call that failed is marked `FAILED`. |

MCP tool annotations are *hints* from the server. The security boundary is RBAC, the namespace allowlist, the tool registration done on the server side, and the Hub's own read/write list.
