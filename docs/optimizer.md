# Resource optimizer

The Hub reads each cluster's usage, sizes every container (a *Sizing*), prices it, allocates cost by namespace and team, reports waste and Savings, and checks its estimate against the cloud Bill. Sizings are read-only until an Operator approves one; the Actuator ([client-cluster.md](client-cluster.md#running-an-actuator)) then applies it in the client's cluster.

## Workload usage

The Hub reads each cluster's Prometheus itself, with no model call, to learn what every Workload's containers use: `squero sizing usage --contract <id> --window 7d` prints it (`--json` too). A Workload is found by following pod owners in kube-state-metrics (a ReplicaSet up to its Deployment or Argo Rollout, a Job up to its CronJob, an ownerless pod as itself, any other owner as it is); pods kube-state-metrics doesn't list are looked up once through the Kubernetes API, which sees live pods only. CPU (cAdvisor's `rate`, so restarts don't skew it) and memory (working set, peak per step) are pooled across a Workload's pods per container, so a Sizing is per replica whatever the replica count; requests, limits, OOM-killed pods and CPU throttling come with them. Every query carries the cluster's namespaces and its label matchers. On a store shared by several clusters or Contracts (Thanos, Mimir), `prometheus_labels` must tell them apart: `squero contracts validate` and the Hub refuse two clusters, in one Contract or two, reading the same Prometheus (however its URL is written) with a namespace in common unless one label has different values in their `prometheus_labels`: `{cluster: eu}` also matches every `{cluster: eu, env: prod}` series, and no labels match every cluster's. `contracts validate` compares URLs as written (offline). The Hub, at start, and the `squero` commands that load one Contract also ask each store who it is (`/api/v1/status/runtimeinfo`'s `startTime`, which Prometheus and Thanos Query give, with that cluster's own token), so two names for one store count as one and are refused the same way. A store that can't say (Mimir, VictoriaMetrics, down) is compared by the addresses its host resolves to, with the same scheme, port and path, and an address in common only marks the stores shared (below): one ingress address often fronts several stores. Replicas behind one name answer each for itself, so two names for an HA pair can still look like two; a Relay's cluster isn't asked. Required: cAdvisor and kube-state-metrics (`kube_pod_owner`, `kube_pod_container_resource_requests`); the command names what is missing, and also reads kube-state-metrics scraped without `honor_labels` (the pod's namespace, pod and container in `exported_*`). A cluster uses the Contract's `prometheus` integration unless it names its own:

```yaml
clusters:
  - name: prod-eu
    context: prod-eu
    namespaces: [shop]
    prometheus_url: https://thanos.acme.example      # optional: else the prometheus integration's
    prometheus_token_secret: thanos-token            # optional, a name in secrets.sops.yaml
    prometheus_labels: {cluster: prod-eu}            # optional: added to every query
```
The agent's own `prometheus` tools take a `cluster` in a Contract with clusters, and query that cluster's Prometheus: its `prometheus_url` and token, else the integration's. A cluster with `prometheus_labels` gets none: labels mark a store shared with other clusters on purpose, and the Hub can't force them into the agent's PromQL as it does into its own queries. The tool's description says so; the agent keeps its Kubernetes tools there, and `sizing_for_workload` when the Contract lists `sizing`. The same goes for a cluster whose Prometheus another Contract also reads, even in other namespaces (which loading allows: the Hub's own queries are scoped by namespace); stores are compared as in that check, by URL, by what each store says it is, or by address where one can't say. A Contract without clusters keeps the tools without `cluster`, on the integration's URL. The health check queries each cluster that has them, so a Contract whose clusters all have none has no Prometheus check.

**GPUs** (slice 17.1, NVIDIA only). A container that requests a GPU (in kube-state-metrics, the window's largest request of `nvidia.com/gpu`, `nvidia.com/gpu.shared` as the device plugin renames time-sliced GPUs, or a MIG profile, one instance each; a sharing scheduler's memory or core quantities such as HAMi's `nvidia.com/gpumem` are not GPUs) gets its GPUs read from NVIDIA's DCGM exporter, run with its Kubernetes mapping on (the exporter chart's `kubernetes: auto`; the binary's own flag is off by default): each GPU its pods were given, by DCGM's `UUID` (else its node and index; a MIG instance by its `GPU_I_ID` too), with its busiest hour, the hours read, its peak memory and the pod last seen on it. The busiest hour is the highest of the window's hourly means of the busy share: the graphics engine's (`DCGM_FI_PROF_GR_ENGINE_UTIL_RATIO`, or its older name `DCGM_FI_PROF_GR_ENGINE_ACTIVE`) where DCGM has it, the GPU's utilization (`DCGM_FI_DEV_GPU_UTIL_RATIO`, or the deprecated `DCGM_FI_DEV_GPU_UTIL` in percent) otherwise. Memory is the framebuffer used (`DCGM_FI_DEV_FB_USED_BYTES`, or the deprecated `DCGM_FI_DEV_FB_USED` in MiB): shown, never judged. A MIG instance, a virtual GPU (DCGM's `vgpu` label) and a GPU requested as `nvidia.com/gpu.shared` are marked shared. The exporter's chart scrapes without `honor_labels`, so a pod's own namespace, name and container are `exported_*`; its old names (`pod_namespace`, `pod_name`, `container_name`) and a scrape with `honor_labels` are read too, and plain `namespace` only when neither of the others is on a series, since it is otherwise the exporter's own: a Contract owning the exporter's namespace gets no other pod's GPUs. Nothing is asked of a cluster where no container requests a GPU; a cluster whose GPUs DCGM doesn't cover is noted ("no GPU use from DCGM for N containers that request GPUs"), and a failed read costs only the GPUs, never the Sizings. `squero sizing usage` shows them (`gpus`, `gpu` in `--json`). A Relay's cluster is read the same way, the Relay passing the Hub's queries on. ponytail: a GPU time-sliced without renaming its resource, and without DCGM's virtual-GPU mode, looks like one pod's.

**Idle GPUs** (slice 17.2a). Each hourly run stores, with a GPU-requesting container's Sizing, each of its GPUs and a verdict: `idle` when its busiest hour in the window of the container's Sizing policy stays under 5% busy, else `busy`; `learning` while it has fewer hours read than the policy's history (a day under `production`); `shared` (a MIG instance, a virtual or time-sliced GPU) and `unread` (no use from DCGM) are not judged. A Workload counts its ready containers' judged GPUs by the share of the window each was held (hours read over the window's hours, at most 1), so a pod that moved across three GPUs in the week counts as one GPU, idle or not: `1 of 4 GPUs idle`. GPUs not judged are said beside it (`; 2 not judged (1 shared, 1 unread)`), so none idle never reads as all busy when DCGM doesn't cover them. With a GPU price (`gpu`, per GPU-hour, in the Contract's or a cluster's `prices`, below) the idle share is priced monthly (730 hours) on its own line beside Waste, never in it: Waste, its cost, the ranking, Savings and the Bill check are unchanged. `squero sizing waste` says the Contract's total and each Workload's (a Workload with idle or unjudged GPUs and no waste is listed too), `--json` adds `gpus` to each Workload and the report, and the weekly digest has a line (`Idle GPUs: 1 of 4 GPUs idle, 1,240.00 USD/month.`) while some are idle or not judged. A priced Contract with a cluster that has no GPU price says so instead of a partial total. The console's Workloads page has the total under the waste, an Idle GPUs column, and in a Workload's detail each GPU with its verdict, busiest hour, hours, share of the window held and peak memory; the Cost page has the total beside the Savings; the Hub MCP server's `sizings` gives `idle_gpus` for the Contract and each Workload, and `cost` its `gpus` (slice 17.2b). Counts show up to two decimals, the share their money is worked out from. Nothing is actuated. A GPU's price comes from a typed `gpu` or, on a list-priced cluster, from its GPU nodes' list prices (17.2c, [Cloud list prices](#cloud-list-prices)). The agent's `sizing_for_workload` doesn't show GPUs (a slice of its own, with its eval rerun).

## Sizings

`squero sizing show --contract <id>` prints each container's Sizing under its Sizing policy: what its requests should be, and whether that means set, raise, lower or keep. Nothing is applied. Under `production`, the default, CPU is the 95th percentile of the last 7 days, recent hours weighted more (half-life 24 hours: a drop is followed in about 4 days, a rise within hours), plus 15%. Memory is the peak, plus 20%, so it follows a drop only once the old peak leaves the window. Then a floor of 10m and 32 MiB, then the policy's maximum if it has one (a capped Sizing is listed as a risk), then the limit: limits are kept, a request never goes above one, and a limit below what the container needs is listed as a risk. Requests are rounded up to a millicore and a MiB, and change only when the difference is at least 10% and at least 10m or 16 MiB. Throttling over 10% of CPU periods or an OOM kill hides the real demand, so CPU is never lowered while throttled, and memory never after an OOM kill; both are listed as risks. A container with under 24 hours of history is still learning.

A container's history is covered time: the time its cluster's Prometheus has usage for (of any container in the Contract's namespaces there), from the container's first sample in the window to its last. A gap in Prometheus counts for nothing, so an hour of data after three days without a scrape is an hour of history. A CronJob between its runs, or a Workload scaled to zero beside others that run, keeps its history. After a long gap a Sizing can be learning again until the window holds what its policy needs: Automation applies nothing new to it meanwhile, the Actuator keeps what it holds, Reflexes go on (a Step-up that reaches its term then is kept for another, its memory peak not being known), and its waste leaves the totals, so the digest's waste goes down by it. One limit: where a Contract's namespaces on a cluster hold only periodic Workloads, only their run times count, so a CronJob of 5 minutes a day stays learning there. Give it a policy with a shorter `history`, or it is ready once anything in those namespaces runs all the time.

## Sizing policies

A policy sets the window, the CPU percentile and its half-life, the headroom, floors and maximums, the change threshold and the history needed before a first Sizing; the throttling and OOM holds are not settings, no policy turns them off. Built-ins:

| | production | high-availability | batch |
|---|---|---|---|
| CPU | weighted p95 + 15% | weighted p99 + 30% | weighted p90 + 10% |
| Memory | peak + 20% | peak + 35% | peak + 15% |
| Window, half-life, history needed | 7 d, 24 h, 24 h | 14 d, 72 h, 72 h | 14 d, 24 h, 24 h |
| Floors | 10m, 32 MiB | 50m, 64 MiB | 10m, 32 MiB |

Your own policies and the rules that pick one go in `contract.yaml`; `squero contracts validate` checks them (ranges, a known `base:`, known policy names in rules):
```yaml
sizing:
  default: production                  # optional; off sizes only what a rule names
  policies:
    lean-agent:                        # a built-in with the settings it names replaced
      base: production                 # production, high-availability or batch
      window: 3d                       # 1h to 90d; half_life 1h to 30d; history up to the window
      cpu: {headroom: 0.10, max: "2"}  # percentile 0.5 to 1, headroom 0 to 3, floor, max
      memory: {floor: 64Mi, max: 4Gi}  # Kubernetes quantities
      threshold: 0.05                  # 0 to 0.5
      replicas: {percentile: 0.25}     # 0 to 0.5: the Floor of a Workload with an HPA
  rules:                               # top to bottom, the first match wins
    - {namespace: payments, policy: high-availability}
    - {namespace: "team-*", name: "checkout-*", policy: lean-agent}   # globs: namespace, name
    - {container: istio-proxy, policy: off}                          # also cluster, kind
    # a Workload's spot comes from the first rule without `container` that matches it: the
    # specific rules go above a namespace-wide one, which would match first
    - {namespace: shop, name: cart, policy: production, automate: true, spot: {ratio: 0.7, on_demand: 2}}  # 16.1c
    - {namespace: shop, kind: CronJob, policy: batch, spot: true}    # its runs on spot (16.3a)
    - {namespace: shop, policy: production, automate: true}          # Automation (Phase 12)
```
After the rules, a Job or CronJob gets `batch`, everything else the default. `automate: true` on a rule is Automation: the Actuator applies its containers' Sizings without an approval ([Automation](client-cluster.md#automation)); it needs a policy other than `off` and a cluster with an `actuator_token_secret` (the one the rule names, if it names one). `startup_boost: 2` beside it (1.5 to 4, refused without `automate`) starts that rule's containers with twice their CPU limit until their pod is Ready ([the Startup boost](client-cluster.md#the-startup-boost)). Built-in names mean the same in every Contract (a standing approval names a policy, ADR 0004), so they and `off` can't be reused. `off` lists the container as excluded. The output names each container's policy, and `history 3.0d of 14d` when Prometheus holds less than the policy's window. Each window a Contract's policies use is read in full, so a policy's OOM kills and throttling are from its own window.

## Waste and risk, stored

Every hour the Hub sizes each Contract with a Prometheus and stores the run in Postgres: a row per container with its policy, state, Sizing, average pods and risks. Waste is the request above the Sizing times the average pods, in cores and bytes: what the Sizings would free with headroom kept, nothing for a container that is learning, raised or held. Average pods counts Running pods from kube-state-metrics' `kube_pod_status_phase` (or, without it, the CPU samples, which `rate` keeps about 5 minutes past a pod's end, so short Jobs read high) over the steps between a container's first and last on which its cluster has any sample: a CronJob averages over the time it doesn't run, and a gap in Prometheus counts for no one. Each risk has a kind: `oom_killed`, `throttled`, `under_requested`, `limit_below_need`, `capped_by_policy`, `request_unset`. Runs are kept hourly for 14 days, then the last of each day for 400. A cluster that fails is stored with its error, and readers keep its last good run, so one dead cluster never blanks another. `squero sizing refresh --contract <id>` stores a run now; `squero sizing waste --contract <id>` (`--json` too) ranks the Workloads by waste, a core weighing as much as 4 GiB without prices, with their risk kinds, what is learning or excluded and any stale cluster. Both need `SQUERO_DATABASE_URL`.

## Unit prices

With `prices:` a Contract's Sizings show money as well as cores and GiB:

```yaml
prices: {currency: EUR, cpu: 0.0316, memory: 0.0042}   # per vCPU-hour and per GiB-hour
clusters:
  - name: eks-prod
    prices: {cpu: 0.040, memory: 0.0053}               # this cluster's own; the currency stays the Contract's
```

Each Workload gets the monthly cost (730 hours) of its waste and of its requests, and the Contract gets both totals. The console's Workloads page, the weekly digest and `squero sizing waste` rank by the waste's cost and show it as `41.20 EUR/month`. Requests count every container that has one, learning or excluded too, while waste counts only sized ones. It is the cost of what pods reserve, not of the nodes: idle node capacity isn't in it. Money is worked out when shown from the stored quantities, so a corrected price applies to every past run, and the digest's change since last week is a change of usage at today's prices. Rows stored before 10.1 hold requests only for ready containers. One currency per Contract, never converted. A price can be 0 (hardware already paid for). A cluster's prices need the Contract's, so every cluster of a priced Contract is priced and they rank together. Without `prices:` nothing changes: cores and GiB, and a core ranks like 4 GiB. The agent's `sizing_for_workload` never shows money. `gpu:` beside `cpu` and `memory` (per GPU-hour, from slice 17.2a) prices [Idle GPUs](#workload-usage); a cluster's own prices without one take the Contract's. A cluster priced from list prices gets its GPU price from them ([below](#cloud-list-prices)); typing its `prices` in full (`cpu`, `memory` and `gpu`) wins over that, as typed prices do. A typed `gpu` is not blended by a spot discount. The [Bill check](#bill-check)'s estimate adds the cluster's GPU-hours at its `gpu`.

## Cloud list prices

Instead of typing `prices:`, a Contract can take them from what its clusters' nodes cost on demand:

```yaml
list_prices: {weight: 7, discount: 0.6, gcp_key_secret: gcp-pricing, currency: USD}   # all optional
clusters:
  - name: eks-prod          # provider, region and instance types come from kube-state-metrics
  - name: on-prem
    prices: {cpu: 0.02, memory: 0.003}                   # typed prices always win
    provider: aws           # only for a cluster that can't say (kube_node_info's provider_id)
```

Each hourly run reads the cluster's nodes (`kube_node_info`, `kube_node_labels`, `kube_node_status_capacity`); kube-state-metrics must allowlist the node labels (`--metric-labels-allowlist=nodes=[node.kubernetes.io/instance-type,topology.kubernetes.io/region]`). Once a day the Hub looks up each (provider, region, instance type) in the cloud's public price list: AWS's offer file (streamed, Linux, shared tenancy), Azure's Retail Prices API (pay-as-you-go Linux, no Spot) and, only with `gcp_key_secret` naming a Billing API key, GCP's catalog (cores and RAM of the machine family, on demand, not custom). A failed lookup is tried again after an hour and keeps the last good price and its age. A cluster's prices are its nodes' total price over their total vCPU and GiB, one vCPU worth `weight` GiB (default 7), so the CPU and GiB prices add back up to the nodes' price exactly; `discount` (0 to 1) multiplies them for a committed-use deal. **GPUs** (slice 17.2c): a node's GPUs come from its `nvidia.com/gpu` capacity. In a cluster with nodes with GPUs and nodes without, the CPU and GiB prices (and the spot shares) are the GPU-less nodes', and what the GPU nodes cost above their vCPU and GiB at those prices (spot ones at the spot rate) is their GPUs', per GPU-hour: the `gpu` that prices [Idle GPUs](#workload-usage), named in the price note (`1 GPUs at 0.334 a GPU-hour`), so the nodes' prices still add back exactly with their GPUs in the Bill check. It is one price for the cluster's GPUs: with several GPU models, each is priced at their average, so an idle cheap GPU reads dearer than it is (type the cluster's prices to set it). With GPUs on every node, nothing sets a CPU and GiB price apart from them: those prices are the whole nodes' as before, the GPUs are unpriced and the note says to type the cluster's prices in full (`cpu`, `memory`, `gpu`); so are GPU nodes that cost no more than their vCPU and GiB at the others' prices. On GCP a machine's list price is its cores and RAM, its GPUs apart: GCP's GPUs stay unpriced, the note saying so. A mixed cluster's CPU and GiB prices drop once its GPUs are priced apart, and with them its waste, requests and Savings in money: the GPUs' share was in them before. ponytail: one GPU price for the cluster's GPU nodes, spot or not, the latest mix's; MIG profiles' capacity isn't counted, and time-sliced GPUs advertised as replicas count each replica, so their price is a replica's; the [nodes that could go](#nodes-that-could-go) are priced by their CPU and memory, a GPU node's GPUs left out. The currency is USD unless `list_prices.currency` (three capitals, e.g. `BRL`) says otherwise: only Azure's and GCP's catalogs offer one, so every cluster must then set `provider: azure` or `provider: gcp`; prices are never converted. On demand only: a cluster's spot nodes are priced from these at its own discount ([Spot nodes](#spot-nodes)). A cluster without labels (kind, bare metal) or without a price yet is not priced, says why, and leaves the whole Contract in cores and GiB, since money for one cluster and cores for the other can't be ranked. `squero sizing prices --contract <id> [--refresh]` shows where each cluster's price comes from, the Cost and Workloads pages and `sizing cost` and `sizing waste` print the same line. `list_prices` and a Contract-level `prices` can't both be set.

### Spot nodes

A cluster that runs spot nodes names their label and what they cost, as a share of on-demand (slice 16.1a):

```yaml
clusters:
  - name: prod
    spot:
      label: karpenter.sh/capacity-type=spot   # key=value; a node without it is on-demand
      discount: 0.35                           # a spot node pays 35% of its on-demand price
      taint: kubernetes.azure.com/scalesetpriority=spot:NoSchedule   # optional: AKS taints its spot nodes
```

The label is the one the cluster's nodes carry: `karpenter.sh/capacity-type=spot` (Karpenter), `eks.amazonaws.com/capacityType=SPOT` (EKS managed node groups), `cloud.google.com/gke-spot=true` (GKE), `kubernetes.azure.com/scalesetpriority=spot` (AKS). `discount` is a multiplier, as `list_prices.discount` is: more than 0, less than 1.

- **List prices**: each spot node costs its **spot list price** where the cloud gives one (from 0.59.0, slice 16.4a), else its on-demand list price at the discount, node by node, before the cluster's CPU and GiB prices are made, so they still add back up to what the nodes cost. The price note says which: "spot list on 2 of 3 nodes, x0.35 on 1 (HTTP 403 from ec2.us-east-1.amazonaws.com)", or "spot x0.35 on 2 of 8 nodes" where none has one. A deal (`list_prices.discount`) is an on-demand node's only: committed-use deals don't cover spot capacity, so a spot node pays its spot list price, or its discount of the list price, and no more. Where the spot prices come from, read daily with on-demand ones and kept, their last good price and its age, in a table of their own:
  - **Azure**: the Retail Prices API's meters named "... Spot" (Linux, not Low Priority), from the read on-demand prices already make.
  - **GCP**: the catalog's `Preemptible` SKUs ("Spot Preemptible N2 Instance Core running in ..."; a legacy "Preemptible" one only where no Spot one is), from the same read.
  - **AWS**: EC2's `DescribeSpotPriceHistory` (Linux/UNIX), read with the Contract's own `aws` integration's key and kept for that Contract alone, never priced into another's: the IAM user needs `ec2:DescribeSpotPriceHistory`. Each instance type of the cluster's spot nodes, in a region among the integration's `regions`: averaged in each zone over the last day, then across the zones. A refused call (no permission) falls back to the discount, the price note saying why.
  - A cluster with typed prices keeps its discount: a negotiated on-demand rate and a public spot price are two kinds of number.
- **Typed prices** (the cluster's or the Contract's) are read as the on-demand rate and blended each hourly run by the cluster's spot and on-demand capacity, by size as a price is split (one vCPU worth `list_prices.weight` GiB, 7 without list prices): "typed prices, spot x0.35 on 1 of 2 nodes: x0.675 of them". A cluster without `spot` keeps its typed price as it is.
- **Every pod costs the cluster's blended price**, wherever it runs: cost by namespace and team, Waste and Savings keep one rate per cluster, which moves as the cluster's mix of spot and on-demand nodes does. A **node that could go** is priced at its own rate: an on-demand node above the blended price, a spot node at the discount.
- **Seen through kube-state-metrics**: allowlist the label (`--metric-labels-allowlist=nodes=[karpenter.sh/capacity-type,...]`). It is named the way kube-state-metrics names it (`label_karpenter_sh_capacity_type`, a capital letter in snake case). Where no node shows it, every node is priced on-demand and the price note and the Nodes page say so. A label set or changed in the Contract counts from the next hourly run.
- **No Actuator needed**: pricing only reads Prometheus. The Nodes page marks each spot node; the Hub MCP's `nodes` says `spot` per node and per cluster.
- **The Bill check** prices each hour's spot capacity at a spot node's rate and the rest at an on-demand one's, the rates the cluster's pricing applies, so its estimate follows the mix the bill charged, not the latest one; the bill counts its spot lines (see [Bill check](#bill-check)).

### Spot ratios and candidates

`spot: {ratio, on_demand}` on a Sizing rule is a [Spot ratio](../CONTEXT.md) (slice 16.1c): the share of its Deployments' and Rollouts' replicas meant for spot nodes, and its On-demand minimum, the replicas kept off them whatever the ratio. On-demand replicas are the larger of the minimum and the share that isn't spot, rounded up: `{ratio: 0.7, on_demand: 2}` gives 10 replicas 3 on-demand and 7 on spot, and 4 replicas 2 and 2. `ratio` is more than 0 and at most 1, `on_demand` 1 or more; both are required. A Workload's ratio is the first rule without `container` that matches it, whatever its policy (`off` too) and with or without `automate`. A rule is refused when it names a `container`, a kind that never runs on spot (StatefulSet, DaemonSet, Job; a CronJob has a rule of its own, below), or reaches no cluster that names its spot label and has an `actuator_token_secret`; on a cluster without both, its Workloads are under no ratio. The Hub tells each cluster's Actuator its Workloads under a ratio (live ones of a kind that can, in the cluster's namespaces; one whose pods block a node by its latest report with no share on spot, every replica kept off spot nodes; the list waits for a usable report and read, the Actuator keeping the last), the spot label and `taint` (the toleration its spot replicas get; only AKS taints spot nodes by default), and the nodes carrying the label as last read; its webhook places them from slice 16.2b, and until it says so in its report the Workloads show "its Actuator doesn't place them yet": the Nodes page and the Hub MCP's `nodes` show, for each live Workload under a ratio, its replicas meant on-demand and on spot against where they run (not known in a read made without the spot label), and why none is meant for spot for a kind that can't, fewer than 2 replicas, or one whose pods block a node in its Actuator's latest report. Once its Actuator's latest usable report says it places them, a Workload with fewer replicas on on-demand nodes than meant shows a risk: "1 on-demand, below its minimum of 2: restart it to repair", or "2 of its 3 on-demand, where all are meant to be" where every replica is (it blocks a node, or has no more replicas than its minimum) (a spot replica that fell back to on-demand is never a risk, and nothing evicts to repair it).

**Candidates**, on every cluster with Prometheus: each Deployment or Rollout with 2 or more replicas on average in the latest Sizings, no pod claiming a persistent volume (`kube_pod_spec_volumes_persistentvolumeclaims_info`), none blocking a node in its Actuator's latest usable report, and under no ratio, with a what-if: 70% of its replicas (an average rounded half up) on spot and 2 on-demand at least; one the what-if moves nothing of (2 replicas, or an average under 2.5) is left out. Where the cluster names its spot nodes and has a price, what that would save a month: its spot replicas times one pod's current requests at the cluster's on-demand rate times one less a spot node's rate against it (the discount, over a deal for a list price; never below 0). An upper bound, a figure of its own, never summed with Savings: nothing is saved unless a spot pool exists and the autoscaler moves nodes to it. Ranked by saving; the first 20 shown, the total counting every one. Without `spot` the replicas and requests show, with "set the cluster's spot to price it". CronJobs: below.

**CronJobs on spot** (slice 16.3a: the Hub's side; its Actuator steers them from 16.3b). A CronJob's runs go on spot whole, by a rule of their own: `{kind: CronJob, ..., spot: true}`, refused on a rule without `kind: CronJob` and with a ratio or minimum on one with it (a batch run that starts again from zero is a judgement of its own). Each run's first tries prefer spot nodes; once the run has a failed pod, its retries are required off them, so a run is interrupted once at most. Only a CronJob whose Jobs allow a retry (`backoffLimit` of 1 or more; the default is 6) and count an interrupted pod as failed (no `podFailurePolicy` that ignores `DisruptionTarget`): kube-state-metrics has no `backoffLimit`, so its Actuator reads them and reports the ones it skips, with why, which the Nodes page shows. The Hub lists a cluster's CronJobs from `kube_cronjob_info`, running or not (one between its runs has no pod to be seen by), sends its Actuator those under `spot: true` in its namespaces, a run that blocks a node or not (a run blocks only while it runs, and a spot node it holds is the cloud's to take anyway), in a list of their own (an Actuator of 0.57.0 ignores it), and the Nodes page says "its runs on spot, a retry off it" with its live pods by side, or why not ("its Actuator doesn't steer its runs yet" until its report says it does, or the reason it skips one): no intended split and no risk (a run that falls back to on-demand is the design). A CronJob under a ratio by a rule without `kind` is told it needs a rule of its own. **Candidates** include every CronJob of the latest Sizings under no rule, its what-if a run entirely on spot: its average pods (no split, kept to three decimal places for a batch run: an hour a night is 0.04) at one less a spot node's rate, "if its Jobs allow a retry", unless its Actuator reported they don't, ranked with the Deployments by saving.

## Bill check

A cluster may name its bill lines with `billing: {tag: "squero-cluster=kind"}` (the Contract needs a Prometheus and the `aws`, `azure` or `gcp` integration; with more than one, the cluster sets `provider:`). AWS: a cost-allocation tag activated in AWS Billing, read from Cost Explorer (`GetCostAndUsage`: EC2 compute, usage before credits, unblended, a day at a time; the `aws` integration's IAM user needs `ce:GetCostAndUsage`). Azure: any resource tag, read from Cost Management (`type: ActualCost`, `PreTaxCost`, the Virtual Machines service, usage charges, a day at a time) with the `azure` integration's service principal (tenant, client id and subscription from its `env`, the client secret from `env_secrets`; it needs Reader or Cost Management Reader); an AKS node pool carries the tag to its scale set, and a day without usage reads as 0. GCP: a label (lowercase letters, digits, `_` and `-`, the key starting with a letter), read from the billing account's BigQuery export, so the cluster also names its table: `billing: {tag: "squero-cluster=kind", table: "my-project.billing.gcp_billing_export_v1_XXXXXX_XXXXXX_XXXXXX"}`. Turn the export on in the Cloud Console (Billing, Billing export, standard usage cost); it holds data only from then on. The `gcp` integration's service account needs BigQuery Data Viewer on the dataset and BigQuery Job User on its own project (`GOOGLE_CLOUD_PROJECT`, where the query runs); for this read alone the Hub mints a token with only the `bigquery.readonly` scope. It sums `cost` (before credits) of Compute Engine's core and RAM SKUs per UTC day, Spot ones ("Spot Preemptible ...") included: shared-core machines (e2-micro, e2-small, e2-medium) and committed-use lines are not counted, nor disks and network. The Hub reads once a day on its hourly run (a failure, a 429 included, is tried again after an hour, about one call per billed cluster a day) and keeps the last 30 full days. `squero sizing bill --contract <id> [--days N] [--refresh] [--json]` and a line on the Cost page set the bill of the last N (default 7, up to 30) full UTC days ending 2 days ago, while the cloud settles them, beside the estimate: the cluster's node capacity-hours (kube-state-metrics, an hourly sample each) at its unit prices, typed or from `list_prices`, and, where the cluster has a GPU price, its nodes' GPU-hours (`nvidia.com/gpu` capacity) at it (slice 17.2c; without a GPU price they aren't read, and on GCP, whose bill is read as its core and RAM lines, they are left out). **Spot** lines count on every cluster, whether or not it sets [`spot`](#spot-nodes): GCP's by their SKUs, Azure's and AWS's as usage of the same service (believed from the clouds' docs, which don't settle it for AWS: unconfirmed until a live check on an AWS cluster). Where the cluster sets `spot`, the estimate prices each hour's capacity on nodes that carried its label at a spot node's rate and the rest at an on-demand one's, and the row says what share of the vCPU-hours ran on spot ("spot: 33% of the vCPU-hours, at x0.35": a spot node's rate against an on-demand one's, so with a deal it is the discount over the deal, x0.583 for 0.35 and a deal of 0.6), or, with none in the window, to allowlist the label if spot nodes ran; a cluster on spot without `spot` shows its estimate above its bill. An Azure day billed in two currencies (an EA account's spot rows are priced in USD whatever its own) fails the read, saying so. **The bill's spot part** (from 0.59.0, slice 16.4b): what a cluster's spot lines cost (`spot_billed`) beside what the estimate prices its spot hours at (`spot_estimated`), a spot price, typed or from the list, checked against what the cloud charged. AWS's and Azure's come from a read of their own after the total's, grouped (Cost Explorer by `USAGE_TYPE`, its `...SpotUsage:<type>` lines; Cost Management by `PricingModel`, its `Spot` rows), so a reply not shaped as expected costs the spot part only: the total and its verdict are saved as before, the last known spot part kept, and the row says "its spot lines failed to read: ...". That is one more call a day per billed cluster (Cost Explorer charges 0.01 USD a request). GCP's export query sums its `Spot Preemptible` and legacy `Preemptible` SKUs with the total: only fields it already reads, one scan. No verdict of its own: the total's gap is the check. A day read before 16.4b has no spot part, the row waiting for the next daily read; a bill with spot lines on a cluster that doesn't name its spot nodes says so. The gap is the estimate's distance from the bill as a fraction of the bill; within 5% is reconciled, else flagged (the CLI exits 1). The estimate counts the node-hours Prometheus sampled: when some hours of the window are missing (a laptop that slept) the row says "the estimate rests on N of M sampled hours", and below 90% of the hours it shows the gap but no verdict (and the CLI doesn't exit 1 for that alone). On GCP, whose export says how many RAM GiB-hours a day's lines charged for, a window with a day billed for fewer than 95% of the GiB-hours its nodes were sampled for, read less than 3 days after that day ended, is **still settling**: the gap and no verdict, and the note names each such day (audit A6a: a newly enabled export was seen still filling a day 28 hours after it ended, complete 30 to 38 hours after; that check's estimate of the nodes' memory was 3% under what GCP billed, so a complete day reads at or above its samples). Every day short is a real gap (a label missing from nodes), and so is a short day read later: both judged as usual. The next daily read of the bill settles it. A bill in another currency than the prices (an Azure subscription billing in BRL needs `list_prices: {currency: BRL}`), a day not yet settled, a failed read or a cluster without a price says why and shows no gap; nothing is converted. Reconcile only: no shown cost changes.

## Cost by namespace

The console's **Cost** page and `squero sizing cost --contract <id> [--json]` group a Contract's latest stored Sizings by namespace (each cluster's own: `kind/lab`, not `lab`): each namespace's requests (every container, learning and excluded ones too), its waste (sized containers), what both cost a month with the Contract's prices (cores and GiB without them), and how many Workloads it has, ranked by what its requests cost. A namespace links to the Workloads page filtered to it. The namespaces add up to the Contract's totals on the Workloads page. It is the cost of what pods reserve in the Contract's namespaces, not of the nodes.

## Cost by label and team

List pod labels and team rules in `contract.yaml`, and the Cost page gets a **Group by** picker (`squero sizing cost --by team` or `--by label:<key>`):

```yaml
allocation:
  labels: [team]                    # read from kube-state-metrics' kube_pod_labels
  teams:                            # first match wins, else "(no team)"
  - {team: payments, namespace: "pay-*"}
  - {team: storefront, labels: {team: storefront}}
  - {team: platform, cluster: kind}
```

kube-state-metrics exports no pod labels unless allowlisted: `--metric-labels-allowlist=pods=[team]` (kube-prometheus-stack: `kube-state-metrics.metricLabelsAllowlist: ["pods=[team]"]`). The Hub reads only the listed keys, takes a Workload's labels from its newest pod (by `kube_pod_created`), and stores them with each hourly run. Team rules are matched when shown, on the cluster, a namespace glob and label values, so a changed rule applies to past runs too. Runs stored before a label was listed have no labels, so only cluster and namespace rules match them. A team or a label value spans clusters, unlike a namespace. Workloads without the label go to `(no <key>)`. When no pod in a cluster has the label, the page and the CLI warn that kube-state-metrics probably doesn't allowlist it.

## Savings, and comparing periods

The Cost page and `sizing cost` name the waste's cost the **available Savings**: what the requests above the Sizings cost, per group and for the whole Contract (cores and GiB without prices). What under-sized containers need on top stays a risk on the Workloads page, never netted against it. **Compare with** (1, 7, 30 or 90 days ago; `squero sizing cost --compare 30d`, any `m`, `h` or `d`) adds each group's change in requests and Savings since then: each cluster's latest run now against its latest run at or before then, both at today's prices, so a price change alone changes nothing. The page names the run each cluster is compared with: after 14 days only one run a day is kept, so it can be a little older than asked. Only what both runs know is compared. A cluster with no run that old is left out, named with its oldest run. A container whose requests weren't stored then (learning or excluded before 0.8.0) is left out. So, when the grouping reads labels, is every container of a cluster where no pod had them then but some do now (stored before the Contract listed them or before kube-state-metrics exported them), which would otherwise seem to move from `(no team)` into its team. Both are listed as left out. A Workload new since counts as new cost, and a group gone since stays listed with its whole drop and no Workloads.

## Realized Savings

Each hourly run compares every container with its cluster's previous good run. A request lowered to within 10% of a Sizing the Hub showed in the 14 days before (one below the old request) is stored as a drop, CPU and memory apart. It is worth (old request − new request) × the container's pods in its latest run, at today's prices (cores and GiB without prices): a monthly run rate, and an amount accrued since the drop, which is that rate × the hours since. A later rise takes the drop back, the newest first, and a drop back at its old request is gone; so a partial rise lowers the accrued amount too. A container gone from a cluster that was read, or whose request was removed, ends its drops; a failed read ends nothing. Fewer pods and raised requests never count as savings, and a drop that matched no Sizing isn't stored. A DaemonSet applied per instance type realizes per type ([below](#a-daemonsets-sizing-per-instance-type)). An HPA's minimum lowered toward its [Floor](#floors) counts here too. `squero sizing savings --contract <id> [--json]` lists each drop; the Cost page shows the totals, and the weekly digest adds *Realized this week* (left out while nothing was realized). Requests and limits are read from the pods seen in the last 5 minutes, so a lowered request shows the next run; a CronJob between runs takes its newest run's (by `kube_pod_created`), what it asks now, so its lowered request realizes after its next run (audit A11); any other container with no live pod (a Workload scaled to 0, kube-state-metrics down) keeps the largest of its window, and such a run neither starts, takes back nor ends a drop. So only a drop between two runs of 0.12.0 or later counts (there is no backfill), and a CronJob's request lowered before audit A11 is never counted: its first run after the upgrade compares with a row from the window's largest. The pods are the latest run's average over its window, as for its waste.

## The weekly Sizing digest

Each Monday at 09:00 UTC the Hub posts a digest of each Contract's stored Sizings to its operator channel, never the client channel: total waste and its change since 7 days before, the nodes that could go ([Nodes](#nodes-that-could-go)), the week's Actuations in one line (`Actuator this week: 5 resized, 1 rolled back, 1 with a Step-up.`: each of resized, rolled back, reverted, failed, with a Step-up and with a Burst counts the containers it reached in the 7 days up to the digest's time, a container reported again counted once; nothing that changed nothing, and no line without an Actuation), the Idle GPUs while some are idle, the top 5 Workloads by waste, risk kinds a Workload didn't have a week before (every risk, under "Risks", while there is no week-old run), stale clusters, how many containers are still learning, and a link to the Workloads page when `SQUERO_CONSOLE_URL` is set. On for every Contract with a `slack:` and a Prometheus when the Hub has `SQUERO_SLACK_BOT_TOKEN`. `sizing: {digest: {schedule: "30 8 * * 5", timezone: Europe/Rome}}` moves it, `sizing: {digest: off}` turns it off. Each due time posts once, also across restarts and missed weeks (claimed in Postgres before posting, so a post Slack refuses is lost for that week, never sent twice). `squero sizing digest --contract <id>` prints it now; `--post` also posts it, leaving the schedule as it is.

## Sizings in a Triage

`- name: sizing` gives the agent `sizing_for_workload`: one Workload's stored Sizing (the Hub's latest run, as the console shows), by the Workload's name or one of its pods' (the longest Workload name the pod name starts with, followed by `-`; `kind` only when two share a name). Per container: the request and limit now, the Sizing and the usage it came from (CPU's weighted p95, memory's peak), the risks, average pods and waste, when the run was and whether its cluster's reads are failing. After an OOM kill a Sizing keeps memory as it is, since the peak is the limit and not the demand, so the tool adds `suggested`: memory request and limit at the policy's memory headroom above the limit (64Mi gets 77Mi), or, with no limit, a request that far above the peak, the node having run out of memory; never past the policy's memory `max` (audit A11), and with a `max` at or below what it was killed at no numbers, only why: raise the max, or look for a leak. The guide asks a Triage of a resource alert to call it once and cite it. It reads only the Contract's own Sizings, of its clusters with a Prometheus and their allowed namespaces; `contracts validate` refuses the integration without such a cluster. The CLI's `squero triage` has no database, so it leaves the tool and its guide out. Rows stored before 0.6.0 have no limits, so they get no suggestion until the next hourly run.

## Needs of autoscaled Workloads

For every Workload with an HPA (a KEDA ScaledObject's `keda-hpa-<name>` is one) the hourly run also reads and stores its **Need**: the replicas it needed, whatever the HPA's minimum and maximum allowed. Nothing is shown yet and nothing is ever written to an HPA: the Need is what the Floor and the Weekly profile (Phase 14) will be computed from, and it is stored now because a profile needs more weeks than most Prometheus keep.

- **The figure.** The HPA's replicas at a time, times the current value of the metric it scales on over that metric's target (4 replicas at 75% of their requests against a target of 50% needed 6); with several metrics, the largest. It works for any metric kind (resource, one container's, pods, object, external), each current value compared with the target of its own type. With no replicas the Need is 0. The replicas counted are the smaller of that moment's and the sample before's: right after a scale-up an HPA reports its new replica count with the utilization of the pods that already have metrics, the old ones, which would read as a Need never there (3 replicas at 83% going to 5 needed 5, not 8).
- **Read from** kube-state-metrics, in the Contract's namespaces only, like every other read of Workloads and pods (the sums behind a node's Room aside: [Nodes](#nodes)): `kube_horizontalpodautoscaler_info` (the Workload an HPA scales), `_status_current_replicas`, `_spec_target_metric` and `_status_target_metric`. No new permission and no Kubernetes API call. A cluster without an HPA costs one query an hour.
- **Unknown**, so nothing is stored for that time: an HPA whose target or current value kube-state-metrics doesn't have (a metric the HPA can't read, or a kube-state-metrics that doesn't export `_spec_target_metric`), a target of zero, and a Workload two HPAs scale.
- **Stored** as each UTC hour's peak per Workload, for 8 weeks. The first read goes back over the 8 weeks Prometheus still has, sampled every 9 minutes; after that each run reads on from the newest hour stored, every minute, so a Hub that was down catches up. An hour read twice keeps the larger figure. A peak between two samples is missed. A failed read is logged and never fails the Sizing run.

## Floors

A **Floor** is the minimum replicas the Hub computes for a Workload with an HPA, from its stored Needs. Each hourly run reads the HPA's minimum and maximum as they are (`kube_horizontalpodautoscaler_spec_min_replicas` and `_spec_max_replicas`) and stores each cluster's Floors, replacing the last. `squero sizing show`, the console's Workloads page (Autoscaled Workloads), the Hub MCP's `sizings` and one line of the weekly digest show them. Nothing is written to an HPA: lowering a minimum is the client's manifest change.

- **The Floor.** A low percentile of the Workload's hourly Needs over its Sizing policy's window, rounded up as an HPA rounds: the 10th under `production` and `batch`, the 25th under `high-availability`, a policy's `replicas: {percentile: 0.10}` (0 to 0.5). Never below 2, unless the HPA's minimum already is. With containers under different policies the highest percentile decides, with that policy's window and history; a Workload whose containers are all `off` gets none.
- **History.** Only the Workload's own stored hours count, each an hour, never the hour under way. Under the policy's `history` (24 hours under `production`) the Floor is learning. Needs are kept 8 weeks, so a Floor looks back 8 weeks at most and never asks for more than 4 weeks of history, whatever the policy says.
- **Against the HPA's minimum.** A Floor below it is a saving: for each stored hour, the replicas the lower minimum would have dropped (the minimum less the larger of the Floor and that hour's Need rounded up, when positive), averaged, each replica at its containers' Sizings (at its request for a container without one). It is its own figure, on top of the Waste: Waste is what every pod asks above its Sizing, this is the pods no longer held. With prices it has a monthly cost. A Floor above the minimum is a risk (`minimum_below_floor`): the Workload needed more in most hours than its minimum guarantees. Equal, nothing is said.
- **The maximum.** No maximum is recommended. Where the Need went above it, one risk says how often: `needed more than its maximum of 5 in 6% of hours`.
- **No Floor**, with the reason shown: two HPAs on the Workload; a minimum kube-state-metrics doesn't have; and a Workload that scales to zero, which is left alone. KEDA gives its HPA a minimum of 1 and scales to zero itself, so scaling to zero is read from the HPA's replicas: 0 at some time in the Contract's longest policy window (8 weeks at most), or an HPA minimum of 0. A Need of 0 is not that: an idle Workload held at its minimum has one, and it is where a Floor saves most. One scaled to zero by hand in that time reads the same and gets no Floor until it is out of the window.
- **Realized.** Each hourly run compares every HPA's minimum with the Floor the last run showed. A minimum lowered while that Floor was below it is stored as a drop, down to the new minimum and never below that Floor: lower is not the Hub's advice, and shows as the `minimum_below_floor` risk. It counts in the [Realized Savings](#realized-savings) with the request drops, listed apart: worth the replicas no longer held (per stored hour since the drop, over the last 7 days at most, the old minimum less the larger of what it counts down to and that hour's Need rounded up, averaged) times the pod's requests as they are now, every container's, at today's prices, as a monthly rate, and accrued as that rate × the hours since. Here a replica counts at what it really asked, not at its Sizing as in the available saving. A minimum raised again takes the drop back, the newest first, and at the old minimum it is gone; an HPA gone, or a second HPA on the Workload, ends it; a failed read or an unknown minimum ends nothing. It is worth nothing until an hour since the drop is stored. No backfill: only a lowering between two runs of 0.49.0 or later counts.
- **Not yet.** The available saving is not in the Cost page's groups.

## Weekly profiles

A Workload with a Floor also gets a **Weekly profile**: its Floors by hour of the week, for load that follows the week. It is shown under the Floor in the console, in `squero sizing show` and in the Hub MCP's `sizings`, and it is stored with the Floor by each hourly run, with its **Backtest**.

- **Each hour of the week** is the median of that hour's Need across the weeks stored, rounded up, never below the Floor. With three weeks, one odd week changes nothing. An hour of the week stored in fewer than three weeks (a gap in Prometheus at that hour in the others) is at the Floor, since one week would decide it; a block can be split there.
- **Three weeks first.** The Workload's own complete stored hours count, over the 8 weeks Needs are kept; under 504 of them the profile is learning.
- **Blocks.** Each run of hours that asks the same, above the Floor, is a block: `Mon 08:45 to Mon 12:00: 7 replicas`. The Floor is the baseline and not listed. A block that asks more than the hour before it starts `sizing.lead_time` early, so the replicas are there when the load is; a block after a higher one starts on the hour. All end on the hour. A week that asks the same in every hour has no pattern, and says so. Blocks are not smoothed, so a noisy week gives many, and a block is not capped at the HPA's maximum: where it asks more, the maximum holds it down, and the Floor's risk line already says the maximum was too low.
- **Settings**, per Contract: `sizing.timezone`, an IANA name the hours are shown and scheduled in (UTC by default), and `sizing.lead_time`, whole minutes from 0 to 2h (15 minutes by default).

  ```yaml
  sizing:
    timezone: Europe/Rome
    lead_time: 30m
  ```

- **KEDA.** For an HPA named `keda-hpa-<name>` each block comes as a `cron` trigger for the ScaledObject `<name>`, to paste beside its other triggers. KEDA holds at least `desiredReplicas` in each window and takes the trigger that asks for most:

  ```yaml
  - type: cron
    metadata:
      timezone: Europe/Rome
      start: 45 8 * * 1
      end: 0 12 * * 1
      desiredReplicas: "7"
  ```

  One trigger per block, each with a single weekday (Sunday is 0): KEDA's docs don't say that the weekday field takes lists or ranges.
- **A plain HPA** has no schedule of its own. It gets the profile with a note saying so: something else has to hold those replicas. The Hub writes nothing and generates no CronJobs.
- **Backtest.** A profile is checked against a week it has not seen: the newest week (the 168 complete hours before the run) is replayed hour by hour against a profile built from the weeks kept before it, three to seven of them. It needs four stored weeks: 504 stored hours before the newest week and at least half of that week (84 hours); until then the profile shows with `not backtested yet (needs four weeks)`.
  - **Needed.** In an hour the Workload needed the larger of its Floor and its Need rounded up, which is what its HPA would run with the Floor as its minimum. So a profile at its Floor in a quiet hour is right, and the profile is judged only on what it adds above the Floor.
  - **Error.** The replica-hours the profile held too few plus those it held too many, as a share of the replica-hours needed. An hour off by less than a tenth of what it needed counts for nothing, like the HPA's own tolerance (with whole replicas that only applies from 11 replicas up). An hour never stored is skipped. The lead time plays no part: the replay is by the hour.
  - **Within the budget** (20%, fixed for now; exactly 20% is within) the profile shows with both parts and what the too many would cost a month, at the Sizings like the Floor's saving: `backtest: off by 12% last week (too few 4%, too many 8%: 3.10 EUR/month)`. That cost is not in the Floors' total: nothing holds those replicas until the profile is applied.
  - **Over the budget** the Workload shows `load isn't weekly enough: off by 34% last week (too few 21%, too many 13%); it keeps its Floor`. Its blocks and its `cron` triggers are not stored and not shown anywhere; the Floor and its saving stand.
- **Limits.** In a zone with daylight saving the hours of the two weeks around a change are an hour off against the rest. The Backtest replays one week, so one unusual newest week (a holiday) fails a good profile until the next week replaces it, and it says how the weeks before predicted the newest one, not how the profile shown (which includes that week) will do next week. The Floor used on both sides is today's.

## Sizings held by an HPA

An HPA with a `Utilization` target on cpu or memory divides the pods' usage by their requests. Changing such a request changes the percentage and so the replica count, which is why the Actuator leaves it alone ([the pre-checks](client-cluster.md#running-an-actuator)). The Hub marks a Sizing that would change such a request as **held by its HPA**: in `squero sizing show`, in the console's Workloads page under the container, and in the Hub MCP's `sizings`. Its Waste still counts, because one manifest change frees it.

- **The change.** The HPA's target as an `AverageValue`: the same threshold in absolute terms. 50% of pods that ask 1200m of CPU in all is 600m per pod. After it the HPA reads no requests, the replica count follows usage as before, and the Actuator resizes that request like any other. The Hub shows it ready to copy:

  ```yaml
  # HorizontalPodAutoscaler shop/api, its cpu metric:
  # 50% of the pod's cpu requests now (1200m), as a value.
  # Apply it before any request changes: a request cut first scales it out.
  target:
    type: AverageValue
    averageValue: 600m
  ```

- **Whose requests.** For a metric of the whole pod, every container's request summed (sidecars too, sized or not), and every container whose Sizing would change it is held. For a per-container metric, that container's own request, and only it is held. The value is computed from the requests as they are now, so apply it before any of them changes: with a request already cut, the HPA has scaled out and the value shown is smaller.
- **KEDA.** An HPA named `keda-hpa-<name>` is taken for the ScaledObject `<name>`'s, and the change is given for its trigger (`metricType: AverageValue`, `value` as a quantity, `containerName` for a per-container trigger). A wrong guess only shows the wrong form.
- **Read from** kube-state-metrics as it is at the run (`kube_horizontalpodautoscaler_info` and `_spec_target_metric`), in the Contract's namespaces; a failed read marks nothing and fails nothing. A target switched to `AverageValue` stops holding at the next hourly run.
- **Limits.** A kube-state-metrics before 2.19 doesn't say which container a per-container metric is of: it reads as the whole pod's, and the comment above the change says which requests the value was taken from. Where a container of the pod has no request for that resource, the HPA's `Utilization` target isn't working at all, so the value shown (from the requests there are, or none) is no equivalent of it. With two HPAs on one Workload the first by name is shown. Nothing is ever written to an HPA or a ScaledObject: the client's GitOps applies the change.

## Nodes

Each hourly run also reads the cluster's nodes from kube-state-metrics and stores the latest read per cluster. The console's **Nodes** page shows them, the Hub MCP's `nodes` gives them to the Operator's client, and the weekly digest has a line on the nodes that could go.

- **Room.** A node's Room is its allocatable CPU and memory less the requests of every pod on it that is Running or Pending. A finished pod holds nothing, though its series stay until it is deleted; init containers are left out.
- **What is read.** Per node: allocatable (`kube_node_status_allocatable`), taints (`kube_node_spec_taint`), whether it is cordoned (`kube_node_spec_unschedulable`), its instance type where the label is allowlisted (`kube_node_labels`), and its pods' requests (`kube_pod_container_resource_requests`, joined to `kube_pod_status_phase` and `kube_pod_info` on the pod's `uid`, a label every pod series carries however it was scraped).
- **Pods outside the Contract's namespaces** are part of a node's Room, so they are read, but only as Prometheus sums them: one total and one count per node, shown as "not visible". No name and no namespace of such a pod reaches the Hub. The Contract's own pods are listed by name with their requests. A cluster behind a Relay is read the same way, through the Relay. On a cluster two Contracts share, each therefore sees how much the other's pods ask per node, as one number.
- **A shared Prometheus.** Node series carry no namespace. Where another Contract reads the same Prometheus and the cluster has no `prometheus_labels`, nothing of this is read (the same guard as for list prices) and the page says why. Give the cluster's series a label (like `cluster: <name>`) and name it in `prometheus_labels` to lift it.
- **The cap on Sizings.** No Sizing asks more than the largest Room after DaemonSets in its cluster: per resource, the most any node has once its DaemonSets' pods are in, among the nodes not cordoned. A Sizing that needs more is capped there and carries the risk `needs_larger_node`. The cap never lowers a request: a container already asking more than that (its node cordoned, or missing from the read) keeps what it has. A DaemonSet's own Sizing is not capped, since that Room already leaves its requests out. When a pod's containers together ask more than that Room, each carries the risk and none is cut. A cluster whose nodes were not read, or only in part (a node without its allocatable), has no cap.
- **Tainted nodes count** toward the largest Room: the Hub can't see a Workload's tolerations, and a cap that is too generous changes nothing, where one too strict would shrink a correct Sizing. CPU and memory may come from different nodes, for the same reason.
- **The autoscaler** is named per cluster in the Contract, never guessed. It decides whose rules a node's Blockers go by.

  ```yaml
  clusters:
    - name: prod
      autoscaler: karpenter   # or cluster-autoscaler; left out: none
  ```

### A DaemonSet's Sizing per instance type

A DaemonSet runs one pod on every node, and one request has to do for all of them: a log collector idles on a small node and works on a large one. The Hub pools a container's pods into one Sizing, so for a DaemonSet that Sizing follows the many. Memory is a peak, so the pooled Sizing fits the busiest pod; its CPU fits the busiest node too: its target is the largest of each node's own percentile (that node's pods over the window, so the pod a rollout replaced counts with its successor), read from kube-state-metrics' `kube_pod_info` (a pod whose node isn't there is its own). A percentile over every pod's samples would sit below a busy minority (one node in thirty, say) and ask far too little for that node's pod. So the pooled Sizing is too large on the quiet nodes.

On a cluster that runs an Actuator, the Hub also sizes a DaemonSet's container **per instance type**: its pods on nodes of one type get a Sizing of their own, from their own usage and against their own requests, under the container's policy. It shows under the container, in the console ("By instance type"), in `squero sizing show` and in the Hub MCP's `sizings` (`by_instance_type`, ten types at most and the rest counted):

```
kind/shop/DaemonSet/agent/app [production]: cpu lower 2000m -> 1150m, memory raise 256Mi -> 1080Mi
  on m5.4xlarge (1 pods): cpu lower 2000m -> 1150m, memory raise 256Mi -> 1080Mi
  on m5.large (2 pods): cpu lower 500m -> 58m, memory lower 256Mi -> 77Mi
```

Here one node of three is busy, and the pooled Sizing follows it: the two small nodes' pods would be asked 1150m where 58m does.

**Applied per type** (from 0.54.0, by an Actuator of that version or later). Where a DaemonSet's container has Sizings per instance type, the Actuator applies those and not the pooled one: each pod gets the Sizing of its node's type.

- **A type with no Sizing yet** (still learning, or a node whose type the Hub doesn't know): its pods get their template's requests, also where an earlier pooled Sizing had changed them.
- **One approval covers every type** of the run it approves. `approve_sizing` is called with the container's pooled values as `sizings` showed them and answers with the types it approved (`by_instance_type`). A container whose pooled Sizing keeps its requests can still be approved when a type's changes them. One with more than the ten types `sizings` shows is refused, since nothing is approved unseen; Automation still applies it.
- **Automation** sends a container when some type's Sizing changes a request, and its churn rule (10% and one lowering a day) is each type's own, against what that type's pods hold.
- **An older Actuator** (before 0.54.0) keeps getting the pooled Sizing for every pod, and nothing for a container only a type of which changes.
- **The money by type** (from 0.54.0). The Hub remembers, per cluster, whether its Actuator applies types (each pull of the desired state says so; stored when it changes). On such a cluster a container with types goes by them only:
  - **Waste** is each ready type's pods against that type's Sizing; a type still learning has none.
  - **The cost of its requests** is each type's pods' requests, and its pods on no known node the container's (the largest any pod asks).
  - **Realized Savings** are each type's pods' request lowered to within 10% of that type's Sizing, worth that type's pods. A drop the container had before its types were applied becomes one per type, from the same run and request, at what each type's pods ask now (a chain of drops still adds up to the first request less what the type asks); a type's drop ends when the type is gone or the types are no longer applied, and an hour whose read of the nodes' types failed changes none.
  - **The pooled Sizing** is shown, not applied: the console opens "By instance type" and says so, the Hub MCP's `sizings` says `applied: by_instance_type`, it raises no risk about a type, and `approve_sizing` refuses it when no type changes a request. Automation sends nothing while every type is still learning.
  - **Nodes that could go after the Sizings** give each of its pods its node's type's Sizing.
- **On a cluster whose Actuator doesn't apply types** (older than 0.54.0) all of this stays on the pooled Sizing. `squero sizing show`, which reads Prometheus without the Hub's store, shows the pooled Waste too. The first weekly digest after a cluster's Actuator starts applying types compares a week by type with a pooled one.

- **Which nodes.** By `node.kubernetes.io/instance-type` (the label list prices need, allowlisted in kube-state-metrics), over the Sizing's window, so the pods of nodes since replaced still count. Nodes without the label are one type of their own. With fewer than two types there is nothing to split and nothing shows. A pod whose node isn't found is in no type; it still counts in the pooled Sizing.
- **Only with an Actuator.** A DaemonSet has one pod template, so nothing but an Actuator resizing each pod in place can give two nodes different requests. On a cluster without one the read isn't made. Nor from a Prometheus another Contract reads without cluster labels: node series carry no namespace.
- **Each type is sized like a container**: the same policy, a day of its own history (a type newly added is still learning), and what hides the container's real demand (throttling, an OOM kill) keeps every type from being lowered.
- **For now it is shown, not applied.** The Actuator still applies the container's one Sizing to every pod, and Waste, Savings and the digest count against that one. Applying each type, and counting Waste by type, come with the next slice (15.3b). Until then the per-type lines say what an Actuator will be able to do.

### Blockers: could a node be removed

A **Blocker** is a pod that keeps its node from being removed. The Nodes page gives each node a verdict: **blocked** (with the pods and why), **clear** ("yes: nothing on it blocks") or **unknown** (with why). It is read-only: the Hub evicts nothing for it, and it does not yet say whether a node's pods would fit elsewhere (that comes with the nodes that could go).

- **Where the facts come from.** A cluster's [Actuator](client-cluster.md#blockers-what-the-actuator-reports) reports the facts of the pods in the Contract's namespaces that may block when they change (it reads them every five minutes), and hourly at least, with its own pod's (audit A4, judged by the same rules, so its node isn't unknown for a pod the Hub can't see): its controller, its emptyDir and hostPath volumes by name, three annotations as they are, and the PodDisruptionBudget covering it that allows the fewest disruptions. It sends facts and no conclusion; the Hub applies the rules, so they can change without redeploying an Actuator.
- **Whose rules.** Those of the autoscaler the Contract names for the cluster, from each one's own documentation:

  | Removes nodes | A pod blocks when |
  |---|---|
  | all three | a PodDisruptionBudget covering it allows no disruption |
  | `cluster-autoscaler` | it is annotated `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`; or, unless annotated `"true"`: it has no controller or a custom one, it has local storage (a hostPath, or an emptyDir not in memory) not all named in `safe-to-evict-local-volumes`, or it is a kube-system pod with no PodDisruptionBudget |
  | `karpenter` | it is annotated `karpenter.sh/do-not-disrupt: "true"`, or with a duration (`"30m"`) and started less than that long ago; any other value is ignored, as Karpenter ignores it |
  | none named | what stops `kubectl drain` without force flags: a pod not managed by a ReplicationController, ReplicaSet, Job or StatefulSet, or a pod using emptyDir |

  A DaemonSet's pods and a node's own static pods stay with their node and block no one.
- **Clear needs evidence.** A node is clear only when every pod on it is known and none blocks. It is unknown when the report was cut at 1000 pods and names no Blocker there, when the Actuator could not read a namespace that has pods on the node, or when the node holds pods the Hub can't see: pods outside the Contract's namespaces that are not a DaemonSet's or static (CoreDNS in kube-system, say), counted from Prometheus and never named.
- **Without a usable report** (the cluster runs no Actuator, it has sent none yet, or its last one reached the Hub more than two hours ago, by the Hub's clock) the Hub goes by what Prometheus shows of the Contract's pods. A pod with no controller, or a custom one, still blocks its node under `kubectl drain`'s and Cluster Autoscaler's rules; under Cluster Autoscaler's the reason adds "unless annotated safe-to-evict: true, which only an Actuator can see". Karpenter has no such rule, so nothing blocks there. A node is never clear this way: volumes, annotations and which pods a PodDisruptionBudget covers stay unseen. Where a budget in a namespace with pods on the node allows no disruption (`kube_poddisruptionbudget_status_pod_disruptions_allowed`), the unknown says so: "the cluster runs no Actuator; PodDisruptionBudget web of shop allows no disruption".
- **Limits.** The autoscaler's own figures are not shown: Cluster Autoscaler's `cluster_autoscaler_unremovable_nodes_count` labels its reasons with numbers that differ between its releases, counts nodes that are simply in use, and keeps a reason's last count once it falls to zero. Karpenter's `do-not-disrupt` on a Node is not read (the Actuator reads no nodes). Cluster Autoscaler's flags are taken at their defaults (`skip-nodes-with-system-pods`, `-local-storage`, `-custom-controller-pods`: all true); a cluster that changed them is judged more strictly than it behaves. A pod that fits nowhere else is not a Blocker here.

### The change that removes a Blocker

Under each blocking pod the Nodes page gives the change that would remove that Blocker ("To remove it"), from the same rules that found it: what to change and what it costs, and a manifest to copy where the change adds something. The Hub writes it nowhere: it belongs in the client's own manifests. The Hub MCP's `nodes` hands the same changes to the Operator's client; for a Contract that masks, the names inside a manifest are placeholders there, and the page has the real ones.

| Blocker | The change | Manifest |
|---|---|---|
| a PodDisruptionBudget allows no disruption | check first that its pods are healthy (a budget also allows none while one is down); then more replicas than it requires, or let it allow one disruption | none: someone set it on purpose |
| annotated `safe-to-evict: "false"`, or `karpenter.sh/do-not-disrupt: "true"` | remove the annotation if the pods may be evicted | none: someone set it on purpose |
| `do-not-disrupt` with a duration | it ends by itself | none |
| no controller, under Cluster Autoscaler | run it under a Deployment, StatefulSet or Job; or accept losing it | the annotation `safe-to-evict: "true"` on the pod, which says in its comment that an evicted pod is gone for good |
| a custom controller's pod, under Cluster Autoscaler | the same annotation, if its controller brings an evicted pod back | the annotation, wherever that controller sets its pods' annotations |
| local storage, under Cluster Autoscaler | accept losing the data when the pod moves | `safe-to-evict-local-volumes` naming every local volume of the pod, on its Workload's pod template |
| a kube-system pod with no budget, under Cluster Autoscaler | give it a PodDisruptionBudget | one allowing one disruption, whose selector is a placeholder to replace with the pod's labels (the Hub reads no labels; as it stands it selects no pod and changes nothing) |
| no controller, a custom controller, emptyDir data, under `kubectl drain`'s rules | the flag of the drain that does it (`--force`, `--delete-emptydir-data`) and what it deletes | none |

- **Where an annotation goes.** On the pod template of the pod's Workload, where the Hub's read resolved one of a kind that has a template (a Deployment, StatefulSet, DaemonSet, Job, ReplicaSet; a CronJob's is under `jobTemplate`); otherwise on the pod itself, and the manifest says so.
- **What it costs is in the manifest**, in its comments: a manifest gets pasted without the page around it. That includes what changing a pod template does: it restarts every pod of the Workload in one rollout (so local data is lost then, not at some later eviction), a CronJob's change reaches only the Jobs started after it, and a Job's template can't be changed once created.
- **Names.** A pod's, a Workload's or a volume's name that isn't shaped like a Kubernetes name never enters a manifest, also when it came from Prometheus and not from an Actuator: a placeholder, or "this pod", stands there instead.
- **Each change lifts its Blocker under the Hub's own rules**: applied to the pod's facts, the reason is gone (tested as a round trip). A budget is lifted by no annotation.
- **The autoscaler's own settings** decide the same for the whole cluster, and the Hub can't read them (they live in kube-system or in objects of no namespace). The page names the ones to check, with their documented defaults when looked up, not the cluster's values: Cluster Autoscaler's `--skip-nodes-with-local-storage`, `--skip-nodes-with-system-pods`, `--skip-nodes-with-custom-controller-pods` and `--scale-down-utilization-threshold`; Karpenter's NodePool `spec.disruption.consolidationPolicy`, `consolidateAfter` and `budgets`. `consolidateAfter` counts from the last pod added to a node or removed from it (Karpenter resets it then; its docs, v1.15, read 2026-11-16), so a node where a CronJob's runs start more often than that is never consolidated (Part A saw one every 3 minutes under `5m`); the Hub can't read the NodePool, so it can't tell which nodes that holds back, and it names the setting rather than warn on every CronJob's node.
- **Not proposed:** the descheduler (its `HighNodeUtilization` needs a scheduler scoring `MostAllocated`, and the default scores `LeastAllocated`), and nothing is turned into a pull request: the Hub MCP's `propose_change` edits a Contract's Sizing policy in the contracts repo, not a client's manifests.

### Nodes that could go

A Sizing frees capacity, but money is saved only when a node leaves. For each cluster the Nodes page says which nodes could go: `Could go now: up to 1 (worker3), 120.00 EUR/month. After the Sizings: up to 2 (worker3, worker2), 240.00 EUR/month.` It is the Hub's arithmetic, on what its hourly run and the cluster's Actuator stored; the Hub removes no node.

- **Which nodes.** A node goes when its verdict is clear (no Blocker, every pod on it known) and each of its pods that would move fits whole on one other node: its CPU, its memory and a pod slot there. Its DaemonSets' and static pods go with it and need no room. A blocked or unknown node never goes, though it can receive. A control-plane node never goes. A cordoned node may go and receives nothing, and neither does a node under a taint Kubernetes set for its condition (not ready, under pressure).
- **Taints.** Pods move only between nodes carrying the same taints, since a Workload's tolerations can't be seen. The taints Kubernetes sets itself (cordon, node conditions) and `PreferNoSchedule` don't count as a difference.
- **What a pod needs of a node.** A moving pod fits only on a node that meets its nodeSelector and its required node affinity (one of its terms, every expression of it), read as the scheduler reads them: a label the node lacks meets `NotIn` and `DoesNotExist`, `Gt` and `Lt` compare integers, `matchFields` the node's name. Under Karpenter its heaviest preferred node affinity term counts too, every one of that weight (Karpenter sorts them unstably, so which one it holds isn't fixed): its scheduler holds it as required while any node could meet it, a new one included, so a pod preferring spot keeps its spot node ("SpotToSpotConsolidation is disabled") unless another spot node has room. The cluster's Actuator reports these from each pod's spec with the nodes' values of the labels they name; a node whose labels it didn't send takes none of the pods that need something of a node. Where the Actuator doesn't report them (one from before this, or one that may not read nodes), no node is counted as one that could go and the page says why. The restart advice of [Placement](#placement) goes by the pod's requirements alone (a restarted pod is placed by the scheduler, where a preference only scores): a pod requiring what no Pinned node has is never advised onto one.
- **The order.** The node asking least goes first, its largest pod is placed first, each pod on the first node by name with room. What a node receives is no longer free, a node that goes receives nothing more, and one that received pods and then goes itself must find room for those too. So the list is one consistent plan, the same from run to run.
- **Twice.** With today's requests, and with the requests after the Sizings: each container with a ready Sizing asks its Sizing (a DaemonSet's applied per instance type, its node's type's), any other keeps its own request (one still learning, one of a pod whose Workload the owner series don't resolve), a container that asks nothing today asks its Sizing, and each node's requests move by what its own pods' did. A Sizing that asks more can also take a node off the list.
- **An upper bound**, shown as one ("up to"): spread, pod affinity, volume zones and tolerations are not seen, nor is the autoscaler's own configuration (Karpenter's `SpotToSpotConsolidation` gate is named among its settings to check).
- **Priced** at each node's capacity (`kube_node_status_capacity`) times the cluster's unit prices, typed or from list prices, for a month, at its own rate where the cluster names [spot nodes](#spot-nodes); in cores and GiB without prices. A figure of its own: it is never added to Waste, Savings or the Floors' total, because after the Sizings it is partly the same money.
- **What "none" says.** The page, the digest and the tool count how many nodes were not judged. A cluster without an Actuator's report has no clear node, so none could go: that is nobody having looked, not a finding. A cluster with [Placement](#placement) where no node shows its label (not allowlisted in kube-state-metrics, or no node labelled yet), or whose nodes weren't read with its label yet, lists none either, the page and the tool saying why (the digest has no line where none could go): a Pinned node would look like any other and be counted as one that could go (audit A5).
- **Every gap means the node stays**: a node read without its allocatable or its pod slots neither goes nor receives, and a cluster's read from before this slice says nothing until the next hourly run.
- **The digest** has one line when a node could go, now or after the Sizings: `Nodes that could go: up to 1 now (120.00 EUR/month), up to 2 after the Sizings (240.00 EUR/month); 3 not judged. An upper bound, not Savings.`
- **Computed when asked**, from the stored read, the Actuator's stored report and the stored Sizings, so it always agrees with the verdicts shown beside it (300 nodes of 30 pods take about 0.2 seconds).
- **The Hub MCP's `nodes`** is the first place an Actuator's strings reach a model. They go out redacted and masked like everything else of the Contract's; a report whose namespace, pod, node or budget name is not shaped like a Kubernetes name is refused when it arrives, and a controller's kind or a volume's name that isn't shaped like one is counted, not repeated.
- **Pinned nodes** (with [Placement](#placement)) never go, and no moving pod is counted to land on one.

### Placement

Pods that can't move keep whatever node they land on. **Placement** gathers them on a few nodes the client keeps for them, the **Pinned nodes**, so the rest can go. The Contract names the nodes' label per cluster, and the taint they carry if any:

```yaml
clusters:
  - name: prod
    actuator_token_secret: prod-actuator
    placement:
      label: squero.io/pinned=yes          # key=value, on the nodes kept for them
      taint: squero.io/pinned=yes:NoSchedule   # optional: tolerated by the pods placed only
```

- **Only with an Actuator** on that cluster: its webhook adds, to each new pod of a placed Workload, a preference for the label (one preferred node affinity term, weight 100, after the pod's own) and, with a taint, its toleration. A preference, never a requirement: a pod with no room on a Pinned node starts elsewhere ([how the Actuator does it](client-cluster.md#placement-gathering-the-pods-that-cant-move), from 0.55.0; with an older Actuator the Hub shows the Pinned nodes and which Workloads it would place, and says nothing about restarting).
- **Which Workloads.** Those whose pods block a node for a reason set in their spec: `safe-to-evict: "false"`, `do-not-disrupt: "true"`, local storage, emptyDir data (each under the rules of the cluster's autoscaler, as for [Blockers](#blockers-could-a-node-be-removed)), on any node, Pinned ones included, so a Workload that has moved keeps the preference at its next rollout. Not for a PodDisruptionBudget that allows no disruption or a timed `do-not-disrupt`: both come and go (a budget allows none during any rollout), and placed for them a Workload would fill the Pinned nodes with pods that can move. Not a pod with no controller or a custom one's, which have no Workload the webhook can name, nor a DaemonSet's. Of a Deployment, StatefulSet, Argo Rollout or CronJob, in the Contract's namespaces, from the Actuator's last report, each pod's Workload as the Actuator names it (none for two hours: the Actuator keeps what it last got).
- **No approval per Workload**: the Contract's field is the consent, as for Reflexes. The pause annotation and the Kill switch stop it.
- **A Pinned node's verdict is pinned**: its Blockers are shown as expected, with no change to remove them.
- **What frees a node.** A running pod's affinity can't be changed, and the Actuator never evicts for Placement: a pod already running moves at its Workload's next rollout or restart. Once the cluster's Actuator places (its report says so), a blocked node says which Workloads to restart to free it ("Restart shop/Deployment/api to free it"), when every Blocker on it is a placed Workload's pod and the Pinned nodes have room for every pod of those Workloads not on one already (a restart moves them all): each pod whole, CPU, memory and a pod slot, largest first, on a Pinned node that takes pods, whatever its taints. Otherwise it says why not: "pod shop/web-1 would still hold it", or "the pinned nodes lack room: about 1.2 cores and 3.0 GiB short". Each node on its own: two nodes' advice may count on the same room. A placed pod that started off the Pinned nodes says "placed, on worker2: the pinned nodes had no room when it started".
- **Seen through kube-state-metrics.** A node label reaches Prometheus only when allowlisted (`--metric-labels-allowlist=nodes=[squero.io/pinned]`, or `[*]`). Where no node shows it, the Nodes page and the Hub MCP's `nodes` say so, and no node is counted as one that could go (a Pinned node would look like any other); a Blocker of a Workload it places gets no change to remove it, its node possibly a Pinned one that keeps it on purpose, and says so. A label set or changed in the Contract counts from the next hourly run's read; until then no node is pinned, none could go, and the page says the nodes were not read with it yet.
- **With Karpenter**, a preference is treated as required when it picks a node to launch and relaxed only when that can't be met, so put the label on a NodePool's template.
- **Shown** on the Nodes page (the cluster's label, how many nodes carry it, the Workloads placed, whether its Actuator places them) and in the Hub MCP's `nodes` (`placement`, `placed_by` on a blocker, `restart` on a node). The digest's line is unchanged.

## The optimizer lab

`make lab` turns the kind cluster into a persistent lab: kube-prometheus-stack (chart pinned in the Makefile, the setup most client clusters run; Prometheus keeps 30 days, Grafana via `make lab-grafana`) and, in namespace `lab`, Workloads with the usage shapes a Sizing must get right: a 24-hour diurnal Deployment with two replicas, an over-requested one, a spiky one, a slow memory leak that its limit OOM-kills about hourly, a CPU-throttled one, an idle one, a StatefulSet, a DaemonSet, a CronJob, and `weekly`, a Deployment under an HPA (CPU at 50%, 2 to 5 replicas; metrics-server is installed for it) whose load follows the week and is shared by its pods: it needs 1 replica at night and at weekends, 3 on weekdays from 08:00 to 18:00 UTC and 7 on Mondays from 09:00 to 12:00, so its Need reads below the minimum and above the maximum. Prometheus is reachable from the Hub on kind's Docker network at `http://squero-control-plane:30090`, so a Contract's cluster can set it as `prometheus_url` with `lab` in its namespaces. Leave the lab running: real history builds up. Its history lives inside the kind node container, so `kind delete cluster` erases it.

A laptop that sleeps leaves gaps in that history, and a Weekly profile needs weeks without them. The lab can run on another host that stays up: `make lab-remote LAB_HOST=<ssh name> LAB_ADDR=<address>` creates a kind cluster `lab` there (the host needs Docker and kind) whose API server and Prometheus listen on that address only. Use a private one, the host's Tailscale address: Prometheus has no login and the kubeconfig, written to `~/k8s_clusters/lab.yaml`, is an admin's. The node container is capped (2.5 CPUs and 6 GiB by default, `LAB_CPUS` and `LAB_MEMORY`) so the host's own services keep theirs, and restarts with Docker. Then `make lab LAB=small CLUSTER=lab KUBECONFIG=~/k8s_clusters/lab.yaml` installs the lab from here. `LAB=small` (`demo/lab/small`) is the lab for a 4-CPU host: the full one asks about 8 CPUs of its node, so there the big Workloads ask and burn a quarter to a third of the CPU, each in the same proportion; the shapes, the ratios of request to usage, `weekly` and all memory are unchanged. A Contract's cluster then sets `prometheus_url: http://<address>:30090`. That is for a Hub on another machine. A Hub on the same host cannot use it: Docker gives one container no way to another's published port through the host's own address, and the read times out. There the Hub joins kind's Docker network (a `compose.override.yaml` with `networks: [default, kind]` for the `hub` service and `kind` as an external network) and the Contract names the node: `http://lab-control-plane:30090`, and `https://lab-control-plane:6443` as the kubeconfig's server, which the API server's certificate covers. For its kubeconfig, apply `demo/lab/hub-read.yaml`: the Hub's read-only role, bound in namespace `lab` only, with a token Secret (`squero-token` in namespace `squero`). A kubeconfig with that token and the cluster's server and CA goes into the Contract's SOPS file (`kubeconfig_secret`); kind's own kubeconfig never does. The same cluster can hold the Triage demo (`make demo CLUSTER=lab`) and a second Contract: `demo/lab/bank.yaml` is a small over-requested Workload in namespace `bank`, and `demo/lab/hub-read-demo.yaml` binds the first account in `demo` and `orders` and gives the second Contract an account of its own in `bank` only, so two Contracts share one cluster and one Prometheus and neither's kubeconfig reads the other's namespaces.
